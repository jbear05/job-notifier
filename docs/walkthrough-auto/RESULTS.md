## Caveat: headless Chrome and Edge, not a windowed Chrome

- **The table comes from headless Google Chrome 157**, the branded build, with Edge 158 as a cross-check. Chrome 157 ignores `--load-extension`, but with `--remote-debugging-pipe --enable-unsafe-extension-debugging` it still loads an unpacked folder through the DevTools protocol (`Extensions.loadUnpacked`), and `Extensions.triggerAction` opens the real toolbar popup for a tab. Edge 158 gave the same result for every step (see "Edge 158 run" below).
- **What headless can't show:** the toolbar, the window, and Chrome's own dialogs. Chrome's permission prompt opens but can't be clicked, so it stays pending. In both browsers the popup closes when the prompt opens, as it does in a windowed Chrome.
- **Two builds:**
  - Run A used the release zip as built (SHA-256 below) for sections 1 to 4, 5.1, 8.4 and 8.5 in the popup, 9.1, 9.2, 10.1, 10.2, 11.1, 11.2, 11.5, and 12.
  - Run B used a test-only copy whose manifest also lists `https://*/*` and `http://*/*` under `host_permissions`, so auto-detect, the overlay, navigation, and isolation could run. Site access was granted and removed through Chrome's own site-access control (`chrome.developerPrivate`, which the Details page uses). On that copy Chrome refuses `chrome.permissions.remove` for what is now a required permission, so "access removed" in 5.3 and the popup trigger of 7.4 stay manual.
- **No Anthropic traffic:** Fetch interception answered every api.anthropic.com request with a mocked reply or error status. The key was the placeholder `sk-ant-placeholder`.
- **Statuses:** PASS means every automated check in the step passed. "Still manual" lists what the run couldn't cover; [release-walkthrough.md](../release-walkthrough.md) lists the same items at the top. Rows X1 to X5 are extra checks that aren't walkthrough steps. Screenshots named in the Evidence column were written to the run's work folder (`<work>/shots/`), not to the repo.

## Findings for the lead

1. **7.1 and 7.2 (not Blockers), `pushState` and hash changes clear the prompt.** Chrome and Edge both fire `tabs.onUpdated` with `{"status":"loading","url":…}` and then `{"status":"complete"}` for `history.pushState` and for `location.hash`. `background.js:532-536` treats any `status: 'loading'` as a full navigation and drops the tab's prompt. In 7.2 the overlay stayed on screen, but Find friends got `NO_POSTING` and called `close()` (`overlay.js:115`). The worker answers `OVERLAY_CLOSE` with `{ ok: false }` when it no longer has a prompt (`background.js:684`), so the frame is never removed. The overlay sat on "Finding friends…" with no request, Close and Escape did nothing, and the full-page frame kept the page unclickable until a reload. In 7.1 the prompt still appeared, because the confirmation showed after the URL change.
2. **8.4 (Blocker), double-click on the overlay's Find friends closes the overlay.** One request goes out (correct), but the first click switches the panel to "Finding friends…", which shrinks the panel to 145 px tall. The second click at the same point (889,269) then lands on the dimmed area, and the scrim handler closes on anything but results (`overlay.js:152-155`). The results never show, although the call is billed. The popup's double-click and Try again are fine.
3. **10.3 (passes, worth a look), the Clipboard API is blocked inside the overlay.** `navigator.clipboard.writeText` rejects with "The Clipboard API has been blocked because of a permissions policy applied to the current document", and `document.featurePolicy.allowsFeature('clipboard-write')` is `false`. `content.js:67` sets `allow="clipboard-write"`, whose default allowlist is the `src` origin, and that is the dynamic `use_dynamic_url` host (`content.js:75`). The frame's document origin is the static extension ID, so the grant doesn't apply. Copy still works through the `execCommand('copy')` fallback in `ui.js:53-72`, and Chrome writes a "Permissions policy violation" line to the console.
4. **Observation (not counted as a FAIL), focus return depends on the page's own focus.** `content.js:64` stores `document.activeElement` when it adds the frame. In early runs the harness reloaded the posting while the page lacked focus (right after the popup closed, or in a background tab). The page's `autofocus` then hadn't run, so the stored element was `<body>` and focus went back to the body after Escape or STOP. Once the harness focused the page first, as a person clicking Apply would, focus returned to **Download receipt** every time in both browsers.

Recorded values: at the `OVERLAY_STATE` pause, `sender.url` was `chrome-extension://<extension ID>/overlay.html`, using the static ID, so `new URL(sender.url).host === chrome.runtime.id` is `true` in both browsers. `sender.frameId` was greater than 0 and `sender.id` matched. The frame's `src` host is a dynamic ID that differs from the extension ID. A `pushState` or hash change logs `"status":"loading"` in both browsers (exact lines are in the "Recorded" line below the table).
